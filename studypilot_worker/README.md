# StudyPilot on Cloudflare Workers

One Worker serves the whole app: the built React frontend as static assets, and
the API under `/api`. Same origin, so there is no CORS to keep in sync and the
frontend calls a relative `/api`.

This is a port of the Django backend in `../studypilot_backend`, which stays in
the repository as a reference and a rollback. Both speak to the same Supabase
database, and their JWTs are interchangeable.

## Layout

| Path | What it holds |
| --- | --- |
| `src/routes/` | One file per Django app, same URLs, same response envelope |
| `src/memory/` | Walrus Memory: record format (`records.ts`) and the reads and writes (`services.ts`) |
| `src/lib/` | Text cleaning, study-context selection, dedup, DeepSeek, caption parsing. Shared with the frontend through the `@shared` alias |
| `src/auth/` | SimpleJWT-compatible tokens, Sui wallet signatures, password checks |
| `supabase/functions/sp-password/` | Password hashing, deployed to Supabase |
| `test/` | Parity tests against values generated by the original Python |

## Things that are not obvious

- **Hyperdrive is required, not an optimisation.** Supabase's database
  certificate is signed by Supabase's own CA and Workers sockets only trust
  public CAs, so a direct TLS connection from the Worker is dropped
  mid-handshake. `src/db.ts` refuses to connect to a remote database without it.
- **The free plan allows about 10ms of CPU per request.** Selecting the study
  context from an 80,000 character PDF costs ~27ms, so the browser does it at
  upload time and the result is stored on the document. Same reason the browser
  parses YouTube captions and assembles the Word file.
- **Password hashing lives in a Supabase Edge Function.** Django's hashes use
  1,000,000+ PBKDF2 iterations; workerd caps WebCrypto PBKDF2 at 100,000, so the
  Worker cannot verify existing passwords at all. The function reads and writes
  Django's format, so accounts keep working either way.
- **Memory records are byte-identical to the Python ones**, so history written
  by either backend is one history.

## Deploying

```bash
npx wrangler login

# Hyperdrive in front of the Supabase pooler (session mode, port 5432).
npx wrangler hyperdrive create studypilot-db --connection-string "$DATABASE_URL" --caching-disabled

# Put the returned id in wrangler.jsonc under "hyperdrive", then set the secrets:
for s in SECRET_KEY SUPABASE_ANON_KEY DEEPSEEK_API_KEY YOUTUBE_API_KEY \
         GOOGLE_BOOKS_API_KEY MEMWAL_PRIVATE_KEY PASSWORD_FN_SECRET; do
  npx wrangler secret put "$s"
done

cd ../studypilot && VITE_API_BASE_URL=/api npm run build && cd -
npx wrangler deploy
```

Caching is disabled on Hyperdrive because students must see their own writes
immediately; it still pools connections, which is most of the benefit here.

## Local development

`wrangler dev` cannot make the Supabase TLS connection either (same CA problem),
so point `DATABASE_URL` in `.dev.vars` at a local TLS proxy on `127.0.0.1`, where
the plaintext hop never leaves the machine. `.dev.vars` is gitignored and holds
the same secrets as above.

```bash
npm test          # 30 tests, including parity with the Python implementation
npm run typecheck
npx wrangler dev  # serves ../studypilot/dist plus the API on :8787
```
